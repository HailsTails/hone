# ESLint runner

The ESLint runner is Hone's embedded mechanism: each selected clause runs as an ESLint rule inside the team's own ESLint setup. Its `exceptionPath` is `embedded`. Core hands it the selected clauses, the files to check, the repository's tracked paths and the exception records for this mechanism. The runner lints the files with its own configuration to find hits, reports every native channel in the team's setup that weakens a selected rule, and writes and checks the projection `disciplines.eslint.mjs`, one slice per config root, that carries the records into the team's own run. Its `projectedKinds` is `["config-override", "inline-disable"]`, so a record can cover only those kinds, and an `inline-disable` only by a file record on its clause and file. It reports no `config-override` on a clause and file that one of the records it is given projects off, since that is the projection's own off-switch.

The native channels, the exception kind each maps to, and how the projection is adopted and checked are in [the guide](../../../../../docs/adding-a-discipline-or-mechanism.md#embedded-mechanisms).

The check compares the committed projection byte for byte with what the runner would write now. Built core is the installed package: the runner reads the package's `package.json` for its name, and the projection imports each piece inside it by package name, `<name>/mechanisms/eslint/...`, which resolves wherever the package is installed. A `package.json` that cannot be read or names no package is a `tool-failed` failure. Core run from source, as in its own tests, imports each piece by its path relative to the folder the slice is written in. A piece outside the install, in the repository's own rule set, is always imported by relative path, and a piece on another drive from a slice's folder fails as `piece-invalid`.

The config roots are the repository root, every folder holding a tracked `eslint.config.*` when the team's lookup is nearest-to-file, and every folder core passes as a declared config root, less any folder at or under a folder with a tracked `disciplines.json`, because nested Hone configurations are not supported yet ([#72](https://github.com/HailsTails/hone/issues/72)). Under the nearest-to-file lookup, `run` returns as `unprojectedFolders` each outermost folder, at or under such a folder and holding a file under check, that holds its own tracked `eslint.config.*`, with the outermost folder holding a `disciplines.json` that holds it as `selectionFolder`: a file there loads that config, which gets no slice, so `hone record-debt` writes no record for it. A folder holding its own `disciplines.json` but no config of its own is not one, since its files load the config above it. When the projection is not in effect, `run` also names each outermost such folder holding files under check whose own config leaves a record of this repository out of effect, or the selected rule off, as a `nested-configuration` slice; core names the folder on the `mechanism-not-run` entry it explains, not as a projection problem. Core reads and validates `eslintConfigRoots` from `disciplines.json` and passes the folders in the request as `declaredConfigRoots`; the runner never reads them itself. Each root's slice is `disciplines.eslint.mjs` in that folder. The root slice holds every record; a package slice holds the records for files under its folder, re-pathed relative to it and glob-escaped as in the root, and every clause-wide carve-out. A file belongs to the deepest root containing it. `project` writes every slice, then, for each tracked `disciplines.eslint.mjs` in a folder that is no longer a root, regenerates the slice that folder would get and removes the file only when its bytes match that text, so it never deletes a file it did not write; otherwise it reports `left-in-place`. `project` renders and reads every slice and orphan before it writes or removes anything, so a failure part-way changes nothing. `run` reports each package slice that is `missing` or `out-of-date`, each declared root with no `eslint.config.*` on disk as `unconfigured`, and, under the nearest-to-file lookup when the projection is not in effect, each package root whose own recorded files under check are not excepted as `not-applied`, grouping the checked files by their governing root once. Every config root gets and keeps its slice whatever a config above it ignores: a lint run from that folder loads its own config and never reads the ignores of the configs above it, so `project` writes the same slices from the same inputs every time. `not-applied` judges each recorded file through the same per-file query as every other judgement, which resolves the file from its nearest config, the one a lint run from its package loads. A root-only repository's projection is unchanged.

## Runtime

- From source, Node 22.18.0 or later, which runs the `.ts` modules directly by stripping types. The built package is plain JavaScript.
- `zod`, for the piece settings, the loaded plugin, ESLint's resolved configuration and the files the runner reads. A dependency of core.
- `@eslint/plugin-kit`, for parsing inline configuration comments. A dependency of core, declared as a caret range whose floor is the version core's lock holds, because a transitive copy does not resolve under strict package managers.
- The repository's own toolchain, as optional peers: `eslint` `^9.39.5 || ^10.15.0`, and `@typescript-eslint/parser` and `@typescript-eslint/eslint-plugin` `^8.73.0`, the latest typescript-eslint 8, whose peer range accepts both ESLint majors. TypeScript is the parser's own peer, so the runner does not check it. The runner loads all three once, when it is loaded, and answers every call with `toolchain-unavailable` naming each that is missing, cannot load or is out of range, or with `toolchain-shadowed` when one resolves from inside the installed core package, before it loads any piece. The suite runs on two lines: ESLint 9.39.5 and 10.15.0, both with typescript-eslint 8.73.0.

## Files

- `create-eslint-runner.ts` builds the runner from its ports: file text, file removal, module loading, paths and ESLint. It implements `run`, `conform` and `project`.
- `eslint-toolchain.ts` loads the toolchain for core's own ESLint run by dynamic imports of `eslint`, `@typescript-eslint/parser` and `@typescript-eslint/eslint-plugin`, so a missing one becomes a named failure. It first asks where each resolves and fails as `toolchain-shadowed` for a copy inside the installed core package, then checks each version against its range, and hands the loaded `ESLint` class to `eslint-instance.ts`, which builds `createEslint` for that version. Core passes only options every supported release accepts: on ESLint 9 it asks for the nearest-to-file configuration lookup with the flag that release names, `v10_config_lookup_from_file`, and ESLint 10 looks up that way by default. It never passes `applySuppressions`, which ESLint 9 refuses and which ESLint 10 accepts with a default of off.
- `eslint-instance.ts` is the port over a loaded toolchain, and takes only types from `eslint` and `@typescript-eslint/parser`. It builds `createEslint` on the loaded `ESLint` class and maps ESLint's results into the runner's own types. It builds a query instance on the team's own configuration, a governance instance on the runner's configuration only, and `lintSourceCases` for conformance. It also defines the reserved rule `<reservedNamespace>/inline-config`. `reservedNamespace` is the `reservedEslintNamespace` field of `core/values/tool-identity.ts`, currently `hone-core`, Hone's own namespace, distinct from every piece's `hone` and `hone-cd<N>` and independent of the package name; the reserved rule, the governance configuration and the projection's block names all take it from there.
- `governing-config.ts` decides, when a nested `eslint.config.*` fails to load, whether the team's own ESLint would ever enter its folder. It asks the config governing that folder, then each config above it up to the repository root, whether it ignores that folder and then the file. `governingConfigIgnores` answers one such question, for a file or a folder, telling a real ignore from a path no `files` block matches; `cachedGoverningIgnores` asks each config about each path once, only when first needed.
- `inline-config-parser.ts` is the adapter for `@eslint/plugin-kit`, the only file that imports it.
- `native-rules.ts` re-exports the ESLint core rules (`eslintCoreRules`) and the typescript-eslint rules (`typescriptEslintRules`) that pieces reuse. It is the only file that imports them, and it imports `eslint/use-at-your-own-risk` and `@typescript-eslint/eslint-plugin` statically, resolved upward from the install like the toolchain.
- `rule-sites.ts` is the one boundary between Hone's pieces and ESLint's rule contract.
  - `siteRule` builds a rule from its `meta` and an `observe` function. `observe` names the sites the rule looks at: `file`, `functions`, `classes`, `calls`, `throws`, `ifs` and `variableDeclarations`.
  - The module maps each site onto the ESLint listener keys it stands for, such as `FunctionDeclaration`, `FunctionExpression` and `ArrowFunctionExpression` for `functions`, in one literal `Rule.RuleListener`, so ESLint's own types check each handler.
  - `functionSiteOf` narrows a node to a `FunctionSite`, or gives `undefined`, for the function types `functions` covers.
  - Its reason to change is ESLint's rule-registration contract: how a rule names the nodes it listens to. On `main` that contract was written in seven plugin files; here it is written once.
  - Four of the seven sites, `calls`, `throws`, `ifs` and `variableDeclarations`, are one node type each. They earn their place only as the price of that single registration point.
  - A new node type for `functions` is added here alone, since every plugin reaches the function types through `FunctionSite` and `functionSiteOf`. A new node type for `classes` is added here and in the class-authoring plugin, which tells a declaration from an expression with a `switch` over `ClassSite` that the compiler holds exhaustive.
- `projection.ts` renders a projection's text, and writes and compares one projection file.
- `projection-slices.ts` finds the config roots for a lookup, names each root's slice, picks and re-paths each slice's records, finds the package root governing a file, and finds tracked slices outside every root.
- `sliced-projection.ts` renders each root's slice, reports stale package slices, and plans then writes, removes or leaves slices for `project`.
- `config-lookup.ts` reads `eslintConfigLookup` from `disciplines.json`, and decides which config the team's ESLint run applies.
- `package-script-scanner.ts` finds ESLint invocations in tracked `package.json` scripts, and the options and `--suppressions-location` values they carry.
- `script-option-effect.ts` judges whether a `-c`, `--config` or `--ignore-pattern` option changes what ESLint does to the checked files under its script's folder. Only one that the folder settles as changing nothing is not reported. An invocation settles only when it is plain: the first command of its script, with nothing before `eslint` but a package runner, `NAME=value` assignments, or `cross-env` followed only by `NAME=value` assignments, and no token after it that the shell expands or that reaches outside the folder. Anything else is reported.
- `suppressions-scanner.ts` reads suppression entries from `eslint-suppressions.json` files and from files named by `--suppressions-location`.
- `eslint-piece-settings-schema.ts`, `eslint-plugin-schema.ts`, `eslint-config-schema.ts` and `eslint-file-schemas.ts` hold the schemas for a piece's settings, a loaded plugin module, ESLint's resolved configuration, and `package.json` and suppressions files.
- `runner.ts` is the runner core loads: the default ports, bound to the toolchain loaded from the install's own resolution.
- `piece-type-packages.json` lists the packages a piece may import types from, `["eslint"]`. It is not the runtime list above.
- `test-fixtures/` holds the consumer repositories that `native-exceptions.integration.test.ts` checks on real ESLint.

## Writing a piece

An ESLint piece lives at `mechanisms/eslint/<DisciplineId>/` beside its `piece.json`. Each clause's settings are `{ "pluginNamespace", "pluginModule", "rule" }`. `pluginModule` is a `.ts` or `.js` path inside the piece folder whose default export is an ESLint plugin, and `rule` must be a key of its `rules`. The rule id is `<pluginNamespace>/<rule>`.

A clause's settings may also carry `options`, a JSON array passed to the rule after its severity. The governance run, the conformance run and the projection all enable the rule as `["error", ...options]`; without `options` the rule gets only the severity.

A piece reuses an ESLint core or typescript-eslint rule by re-exporting it from its plugin module through `native-rules.ts`: `eslintCoreRules` for core rules and `typescriptEslintRules` for typescript-eslint rules. A piece does not import `eslint` rules or `@typescript-eslint/eslint-plugin` directly.

Both take the rules to read from as `NativeRuleSources`. A piece that wraps native rules exports `createPlugin(sources)` and builds its default export from `defaultNativeRuleSources`, so a test can hand it the rules of another ESLint or typescript-eslint line. In an install the default sources are the copies that resolve from the repository root: the same copies core's own ESLint run loads. When a package in a monorepo lints with its own, different `eslint`, its run wraps the root's rules, not its own.

The namespace `reservedNamespace` names (currently `hone-core`) is reserved. Two selected clauses may not share a rule id, or a namespace with different plugin modules. A bad setting, a module that fails to load or does not match its schema, or a missing rule makes the run fail as `piece-invalid`.

The rule imports only types from `eslint` and gets everything else from ESLint's rule context. A shipped piece writes each of its own rules with `siteRule` from `rule-sites.ts`, asking for the sites it looks at rather than ESLint's listener keys. Each handler receives the official ESTree node, which the rule reads and narrows on `type` as it needs. The guide (`docs/adding-a-discipline-or-mechanism.md`) walks through a shipped piece as the example.
